# W3 复盘：课件 RAG、题目入口、联网检索

> 这份文档是给你“学”的，不是给验收看的。先看第 1 节建立整体图，再看第 2～6 节跟一条数据怎么流动；代码细节按需查第 7 节的代码地图。

## 1. W3 一句话

把三件事接起来：

1. **课件变成能查的资料**：PPTX/PDF/Word/Markdown/TXT → 切块 → 分词 → SQLite；
2. **题目变成能确认的输入**：粘贴/上传/拍照 → 转写 → 用户确认 → 才能讲解；
3. **回答有出处**：本地资料用 `[L1]`，网页用 `[W1]`，资料没有就直说。

```text
PPTX / PDF / DOCX
        │  parse_file()
        ▼
   ParsedChunk(文本 + 第几页/第几张)
        │  split_text(600, 80)
        ▼
   chunks 表（text + tokens + course + chapter）
        │
用户提问 ──► Agent 循环 ──► search_notes ──► BM25 top-4 ──► [L1]… ──► 回答
                              │
                              └──► web_search ──► Tavily ──► [W1]… ──► 回答

图片 ──► Qwen-VL 只转写 ──► draft 题目 ──► 用户确认 ──► confirmed ──► 讲题
```

注意：`web_search` 不是每次都调。提示词要求**先查本地**，本地没有覆盖、问题涉及最新信息，或用户明确要求联网时才查网页。

## 2. 课件是怎么入库的

### 2.1 解析：不同文件，最后都变成同一种东西

入口在 `app/rag/parser.py`：

```python
@dataclass
class ParsedChunk:
    text: str
    location: str
```

- `parse_file(path)` 按后缀分发：`.pptx` → `_parse_pptx`，`.pdf` → `_parse_pdf`，`.docx` → `_parse_docx`，`.md/.txt` → `_parse_text`。
- PPTX 会抽文本框、表格、备注；PDF 用 `pypdf` 抽每页文字；位置分别记成「第 N 张幻灯片」「第 N 页」。
- 扫描版 PDF 没有文字层，`_parse_pdf` 会抛 `ParseError`，提示你转文字版或走拍照识别。**不要在这里硬做 OCR**，OCR 是另一条链路。

### 2.2 切块：为什么要 600/80

`split_text(text, size=600, overlap=80)`：

- 一次检索不能把整本 729 页塞给模型，所以先切小块；
- 600 字大约是一页 PPT 讲一个知识点的量；
- 80 字重叠，防止一个公式/一句话正好被切在边界上；
- 切的时候优先在换行处断开，不硬切句子。

`ParsedChunk.location` 会跟着块一起入库，所以最后引用能精确到「第 3 张幻灯片」，而不是只说“课件里”。

### 2.3 分词：为什么不用 jieba

`app/rag/tokenizer.py` 的策略：

- 英文/数字按整词：`dynamic`、`0-1`；
- 中文按**二元组**：`动态规划` → `动态` + `态规` + `规划`；
- 去掉「的、了、是、什么、怎么」这类停用词。

不引入 jieba 的原因：课程名词用二元组已经够召回，零依赖、可解释，出问题能一眼看懂。代价是会有一些无意义组合，但 BM25 的 IDF 会把“到处都出现”的词压下去。

### 2.4 入库：文件名也参与打分

`app/rag/ingest.py` 的 `ingest_path()` 做三件事：

1. 解析文件，拿到 `ParsedChunk` 列表；
2. 建 `Document`（一门课、一个章节、原始文件名）；
3. 每个 chunk 存 `text` 和 `tokens`。

关键在这几行：

```python
tokens = (
    tokenize(piece.text)
    + tokenize(document.filename) * 3
    + tokenize(document.chapter) * 2
)
```

文件名重复 3 次、章节重复 2 次，相当于**标题加权**。问「0-1 背包」时，文件名里带「背包」的课件会更容易排前面。

### 2.5 检索：BM25 在做什么

`app/rag/retriever.py` 的 `search_chunks()`：

```python
search_chunks(
    user_id: int,
    query: str,
    course: str | None = None,
    chapter: str | None = None,
    top_k: int = 4,
) -> list[RetrievedChunk]
```

它做了四步：

1. 按 `user_id` 过滤，保证 A 的资料不会检索给 B；
2. 有 `course` 就只查这门课，有 `chapter` 就只查这一章；
3. 对每个 chunk 算 BM25 分数；
4. 按分数排序，取 top-k。

BM25 的核心是两件事：

- **TF**：查询词在这块里出现得越多，分越高；
- **IDF**：这个词在越多块里出现，越不值钱（比如“算法”到处都是，区分度低）。

代码里 `k1=1.5, b=0.75` 是 BM25 的常用参数；`b` 负责惩罚过长的块，避免“块越长越占便宜”。

另外还有一个很实用的加分：

```python
name_hits = len(query_set & set(tokenize(row.filename)))
score += name_hits * 5.0
```

这就是“文件名命中”的人工加权。

### 2.6 为什么是 SQLite + BM25，不是 Chroma

原计划是 SQLite + Chroma + BGE embedding。实际换成 BM25，原因很具体：

- 当前是 Python 3.14，Chroma/BGE 的依赖重，装起来容易卡；
- 数据量只有 61 份课件、约一两千个 chunk，全量 BM25 打分足够快；
- BM25 不需要下载模型、不需要 GPU，出问题能解释清楚。

这不是“永远不用向量检索”。`search_chunks()` 是一个可替换的边界：以后要换向量库，只改这个函数，工具和接口不用动。

## 3. Agent 是怎么用资料的

### 3.1 工具协议

`app/tools/base.py` 的 `BaseTool` 规定每个工具都有：

```python
name: str
description: str
parameters: dict
async def run(self, user_id: int, arguments: dict) -> str
```

模型看到的是 `description` + `parameters` 的 JSON Schema；真正执行的是 `run()`。

### 3.2 `search_notes`

`app/tools/search_notes.py`：

- name：`search_notes`
- 参数：`query`（必填）、`course`、`top_k`
- 返回格式：

```text
[L1] ch03-动态规划.pptx / 第 12 张幻灯片
……片段正文……
```

`[L1]` 是**代码加的编号**，不是模型编的。模型拿到这段文本后，提示词要求它在回答里引用 `[L1]`。

### 3.3 课程自动注入

`app/api/chat.py` 里，会话有 `course`。调用 `search_notes` 时，`execute_tool` 会把当前会话的课程自动塞进参数，模型不用每次自己猜“现在是哪门课”。

### 3.4 联网检索

`app/tools/web_search.py` 的 `WebSearchTool`：

- 调 Tavily `/search`；
- 返回 `[W1] 标题 / URL / 摘要`；
- 没配 `TAVILY_API_KEY` 时抛 `ToolError`，模型会看到一段可读提示，而不是服务崩掉；
- 网页结果末尾会提醒“可能过时，关键结论点开链接核对”。

提示词里的优先级是：

```text
本地 search_notes 优先
  → 本地没覆盖 / 需要最新信息 / 用户明确要求
  → 才 web_search
```

冲突时以课程资料为准，并说明差异。这是“课程助手”和“通用搜索”的区别。

## 4. 题目入口：为什么一定要确认

### 4.1 三种入口

`app/api/questions.py`：

- `POST /api/questions/text`：粘贴文字；
- `POST /api/questions/upload`：图片/PDF/PPTX/DOCX/MD/TXT；
- 图片走 `transcribe_image()`，文档走 `parse_file()`。

图片限制 10MB，文档 20MB；题目图存在 `data/uploads/questions/{user_id}/`，**不进 chunks**。题目是“这次要讲的题”，不是“课程资料”，混进去会污染检索。

### 4.2 Qwen-VL 只做转写

`app/agent/vision.py` 的提示词写死了：

- 只转写，不解答，不总结；
- 保留题号、选项、单位、上下标；
- 公式用 LaTeX；
- 看不清写 `[看不清]`，不要猜。

图片先做 EXIF 转正，再压到最长边 1600px、JPEG 85。手机照片方向经常是横的，不转正模型会看到躺着的题。

### 4.3 draft → confirmed

新题目一律是 `draft`。`POST /api/questions/{id}/confirm` 才改成 `confirmed`，确认时可以顺手改 OCR 错字。

`app/api/chat.py` 里，带 `question_id` 提问时：

```python
if question.status != "confirmed":
    raise HTTPException(409, "这道题还没有确认……")
```

只有 confirmed 才会把题干拼进模型消息：

```text
用户的话

【待讲题目】
……题干……
```

**为什么要多这一步？** 因为 OCR 一定会错。如果直接拿 draft 去讲，模型可能一本正经地讲一道错题；先让用户看一眼、改一下，成本很低，收益很大。

## 5. L3 考前自测

`app/api/quizzes.py`：

1. `POST /api/quizzes/generate`：按课程/章节检索 top-8 课件片段，让 DeepSeek 只输出 JSON 数组；
2. 代码校验：每题必须有 4 个选项、答案必须是 A–D，不合格的题直接丢掉；
3. `GET /api/quizzes/{id}`：**不返回答案**；
4. `POST /api/quizzes/{id}/submit`：提交后统一判分，返回 `score / percent / 每题解析`。

关键设计：**生成时不让模型“自由发挥”**，只给它检索到的课件片段；没有片段就 400，不凭空出题。提交前不泄题，提交后才给答案。

## 6. 科目隔离和学习记录

- `ChatSession.course`：一个会话只属于一门课；
- 同一会话换科目 → 409；
- `GET /api/sessions?course=&q=`：按科目、标题/消息关键词找历史；
- `GET /api/sessions/{id}/messages`：回看消息；
- `PATCH /api/sessions/{id}`：改标题；有消息的会话不能改科目。

这些不是“多加点字段”，而是防止两门课的历史混在一起，导致检索和上下文串科。

## 8. 踩过的坑（这些比代码更值钱）

### 坑 1：模型名不是想当然

`.env` 的 Key 可用，不代表模型名可用。`qwen-vl-plus` 在当前 DashScope 账号下直接 404：

```text
Model not exist.
```

查 `/compatible-mode/v1/models` 后才发现要用 `qwen3-vl-plus`。教训：**接第三方模型，先列模型，再写代码**；404 不一定是 Key 错。

### 坑 2：验收脚本也会骗人

第一次 10 张截图只有 6/10，看起来像 OCR 不行。实际是脚本拿“答案关键词”去检查“只有题干的截图”，q04/q05/q07/q10 本来就不该出现答案。改成题干真实词后 10/10。

教训：**测试失败先分清是产品错、脚本错，还是预期错**。

### 坑 3：模型不会自动查资料

问“算法的时间复杂度是什么”，模型直接凭常识答了，没调 `search_notes`，自然没有 `[L]`。把提问改成「请先查课件再回答」后，4/4 都走了检索。

这不是模型“不听话”，是提示词和问题本身没有给它“必须查”的信号。验收时要设计能触发工具的提问。

### 坑 4：PPTX 不是万能的

PPTX 只抽文字，公式图片、SmartArt、部分文本框会丢。公式多的课，优先让用户导出 PDF；扫描版 PDF 没有文字层，只能走拍照 OCR。

### 坑 5：SSE 现在是“伪流式”

`app/api/chat.py` 的 `_chunks()` 是把**最终回答**按 24 字切块再发，不是模型逐 token 流式。这样 W2 能先把工具链路跑通；真正逐 token 流式留到 W5 前端一起优化。

## 10. 自测：能答上来就说明你真看懂了

1. 为什么先切块再检索，不把整本 PDF 塞给模型？
2. BM25 里的 IDF 解决什么问题？
3. 为什么入库时要把文件名重复 3 次？
4. 为什么 draft 题目不能直接进入讲解？
5. `[L1]` 是模型生成的，还是代码生成的？
6. 为什么 `question_id` 要在 chat 接口里再查一次数据库？
7. 没配 Tavily Key 时，整条链路会怎么降级？
8. 为什么说现在的 SSE 是“伪流式”？

简短答案：

1. 上下文有限、贵、噪声大；切块才能只取相关片段。
2. 压掉“到处都有”的常见词，让稀有词更有区分度。
3. 做标题加权，让文件名命中课程关键词的课件排前面。
4. OCR 会错，先让用户确认，避免“一本正经讲错题”。
5. 代码生成；模型只负责在回答里引用这个编号。
6. 防止拿别人的题、防止 draft 绕过确认、防止科目串库。
7. `web_search` 返回可读的“未配置”提示，本地检索和文字/PDF/PPTX 不受影响。
8. 因为它是先拿到完整回答，再按 24 字切块发给前端，不是模型逐 token 推送。

## 11. 接下来

W3 的结构不用再动。W4 按大纲做三块：

1. **解题老师**：首轮只给提示 → 「继续」给下一步 → 「直接看答案」给完整解答；固定格式；计算题用 `calculator` 复核；
2. **生活伴侣**：人格提示词、长期记忆、情绪识别；
3. **待办推送**：`remind_at` / `reminded_at` + `push_channels` + 每 30 秒扫描 + PushPlus。

下一步先从解题老师开始，因为它复用 W3 的题目入口和 `[L]` 引用，改动最集中。
